| #   | 讨厌的表现                                                             | XUNO 是否踩中 | 严重度 | 详细分析                                                                                                                                                                                   |
| --- | ---------------------------------------------------------------------- | ------------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **技术自嗨**：花 30 秒讲架构图、模型名称、算法细节，评委听不懂也不想听 | **踩中**      | 🔴     | §17.4 的 Demo 路径在 1:45-2:15 花 30 秒展示"6 层漏斗可视化"。这是给技术评委看的，但大部分评委是企业家/投资人/教育专家。他们听到"六层漏斗"时的内心 OS："又一个学生在讲技术架构，下一个吧。" |
| 2   | **没有真实数据**：所有数据都是"预计""计划""预期"，没有一个是真实的     | **接近踩中**  | 🟠     | 商业计划中所有数字都是理论推导：CTR 预期 15%、付费转化率 3-5%、ARPU 2-4 元。没有一个数字有实际用户验证。如果评委追问"你的推荐准确率实测是多少？"，答案是"还没测"。                         |
| 3   | **读 PPT 式路演**：照着 PPT 念，没有互动感、没有激情、没有故事         | **暂未踩中**  | 🟢     | 文档设计了多层叙事和 Demo 互动，如果执行到位，这个能避免。但风险在于：如果 Demo 现场 API 挂了或 App 崩了，只能 fallback 到读 PPT。                                                         |

### 额外发现的 2 个隐形雷区

| #   | 隐形雷区                               | 风险                                                                                                                                                                         |
| --- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4   | **"无性别"叙事在评委中的接受度不确定** | 🟠 中国评委群体年龄 40-60 岁，部分对"无性别"概念可能持保留态度。如果重点强调"无性别"而非"全人群覆盖"，可能适得其反。建议叙事调整为"不分男女，只看场景和风格"——更务实的表述。 |
| 5   | **Demo 依赖网络和 API 的稳定性**       | 🔴 Demo 现场如果 GLM-4-Flash API 延迟 >5 秒或虚拟试穿 API 超时，整个 Demo 就崩了。**必须有完整的本地录制视频作为 Plan B**，而且这个视频的质量要等同于现场 Demo。             |

### 修复建议

1. **技术展示从"讲架构"改为"讲洞察"**：不说"我们用 FashionSigLIP 做向量检索"，而是说"AI 看到你穿深色好看，是因为你的肤色偏暖——来，看这个匹配度分析"。把技术翻译成用户能感知的结果。

2. **准备至少 3 个"真实数据点"**：哪怕是 48 小时内跑出来的——比如"我们用 5 个测试用户跑了 50 次推荐，匹配度 78%"。比"预计 CTR 15%"有说服力 100 倍。

3. **Demo 视频 Plan B**：提前录制一个完整的 2:20 Demo 视频，画面质量要高（不是手机录屏，是模拟器高清录屏+后期剪辑）。现场如果网络不稳，直接放视频+口述旁白。

## 5. 技术可视化可行性 — 评分 4/10

### 可行性详细分析

#### 6 层漏斗可视化

**当前状态**：漏斗的 6 层逻辑定义清晰（L1-L6），但数据管道未接通。

**48 小时内能做什么**：

- 用硬编码的 Mock 数据做一个静态漏斗动画（各层数字从大变小） — 可行
- 接通真实推荐管道，实时展示每层过滤 — 不可行（管道本身还没跑通）

**风险**：

- Mock 数据的漏斗如果数字太"整"（比如 1000→800→200→120→80→5→3），评委会觉得是编的
- 如果漏斗没有任何视觉动态（只有数字变化），评委 3 秒就看完了，剩下 12 秒是无聊

**最低可行版本（8 小时）**：

```
用一个预设用户 Profile + 100 条 Mock 商品：
- 每层过滤前后的商品数量变化（带动画）

- 最终 3 件商品的缩略图展示
```

#### FashionSigLIP 热力图

**当前状态**：还在用 FashionCLIP（CVPR 2022），SigLIP 替换在 Sprint 后计划中。

**48 小时内能做什么**：

- 用 FashionCLIP 做一个简化版"匹配度可视化"（不用热力图，用进度条或分数） — 可行
- 真正的 SigLIP 热力图 — 不可行

**建议降级方案（4 小时）**：

```
不做热力图，做"匹配度雷达图"：
  - 体型匹配度：85%
  - 场景匹配度：92%
  - 色彩匹配度：78%
  - 风格匹配度：88%
  - 预算匹配度：95%
  → 综合匹配度：87%

这个在 48 小时内完全可行（用 recharts 的 RadarChart），
而且评委 3 秒就能理解"为什么推荐这件"。
```

#### 推荐解释可视化

**当前状态**：有设计但未实现。

**48 小时内能做什么**：

- 展示推荐解释的文字（LLM 生成） — 可行
- 展示"规则引擎版本"和"LLM 润色版本"的对比 — 可行但意义不大

## 6. "哇"时刻设计 — 评分 3/10

> 🔴 致命问题：面试穿搭场景的"哇"时刻根本不是"哇"，是"哦"

### 什么是真正的"哇"时刻？

评委的"哇"需要满足以下条件之一：

1. **不可能的瞬间**："等等，AI 怎么知道这个？"（技术惊奇）
2. **情感共鸣**："这个产品真的在帮我。"（情感惊奇）
3. **简洁到极致**："就这么简单？"（体验惊奇）
4. **数字震撼**："这个数据太猛了。"（数据惊奇）

### 当前设计的"哇"时刻分析

| 设计的"哇"时刻      | 评委实际反应                     | 问题                                                        |
| ------------------- | -------------------------------- | ----------------------------------------------------------- |
| AI 首屏主动推送推荐 | "还行，但也就是推荐嘛"           | 🔴 豆包/ChatGPT 已经让评委习惯了"AI 主动推荐"，这不是新奇事 |
| 对话式逐步逼近      | "有点意思"                       | 🟡 像一个更好的 ChatGPT 对话，不够惊艳                      |
| 实时试穿            | "嗯，试穿效果还行"               | 🔴 淘宝/京东都有虚拟试穿，XUNO 的效果不一定比它们好         |
| 6 层漏斗可视化      | "这学生技术还行"                 | 🔴 这是给你自己的技术团队看的，不是给评委的                 |
| 切换用户推荐不同    | "每个人推荐不一样不是应该的吗？" | 🔴 个性化推荐是 2026 年的标配，不是亮点                     |

### 真正的"哇"时刻应该是什么？

**3 个候选"哇"时刻（选 1 个做透）**：

#### 候选 A：语音一步到位（推荐）

```
评委看到：
  [创始人按住语音按钮，说"伊伊，我后天有面试，互联网公司"]
  [2 秒后，伊伊语音回复"互联网公司建议 Smart Casual"]
  [屏幕同时展示 3 套搭配方案]
  [创始人点击"试穿"，3 秒后展示穿在自己身上的效果图]

为什么"哇"：
  从语音输入到完整方案，全程 <10 秒。
  评委用过 ChatGPT，但从没见过"说话→穿搭方案→试穿效果"这么快的闭环。
  这是"简洁到极致"的惊奇。

执行要求：
  - STT 必须准确（Android 原生 SpeechRecognizer，中文识别率约 90%+）
  - 伊伊回复必须在 3 秒内（需要预生成热门场景的推荐结果）
  - 试穿效果必须提前缓存（不能现场等 API 生成）
```

#### 候选 B：记忆能力展示

```
评委看到：
  创始人: "伊伊，我不喜欢高领的"
  伊伊: "记住了，以后都推荐圆领和V领"
  [展示推荐结果：所有推荐都是圆领/V领]

  创始人: "再给我搭一套约会穿的"
  伊伊: "约会的话，建议试试这件 V 领针织衫配你上次的黑色直筒裤
         ——对，你说过不喜欢高领，这件是 V 领的"

为什么"哇"：
  AI 记住了用户 5 分钟前说的偏好，并且在新的场景中主动应用。
  这是"AI 怎么知道这个？"的惊奇。
  评委立刻想到："如果它记一周/一个月的偏好，岂不是比任何时尚博主都懂我？"

执行要求：
  - 需要实现偏好记忆的写入和读取（Redis 即可）
  - 需要对话上下文传递到推荐管道
  - 48 小时内可行（简化版：硬编码几个偏好 + 展示过滤效果）
```

#### 候选 C：对比冲击

```
评委看到：
  左边：淘宝 App 的 AI 试衣间入口路径（首页→分类→...→4层后到达）
  右边：XUNO 首页直接展示今日穿搭方案

  左边：淘宝推荐"你可能喜欢"（通用推荐，无场景感知）
  右边：XUNO 推荐"明天面试，互联网公司，3 套 Smart Casual"（场景感知）

  左边：淘宝试穿效果（贴图式，不真实）
  右边：XUNO 试穿效果（AI 生成，带体型适配）

为什么"哇"：
  并排对比让差距可视化，评委不需要听你解释，看一眼就懂。
  这是"简洁到极致"的惊奇。

执行要求：
  - 需要提前准备淘宝 App 的录屏（3 个对比点）
  - XUNO 的对应功能必须流畅
  - 投入低，效果好
```

### 最终建议

**选候选 A（语音一步到位）+ 候选 B（记忆能力）组合**。

理由：

- A 解决"体验惊奇"
- B 解决"技术惊奇"
- C 可以作为 PPT 第 7 页的静态对比，不需要在 Demo 中展示

## 8. Q&A 最难的 5 个问题 — 评分 5/10

> 🟠 重要风险：有准备但不够深入，关键问题会露馅

### 问题 1：你的技术壁垒在哪里？别人复制你需要多久？

**评委为什么问**：这是所有互联网+项目的必问题。评委已经听了 20 个"AI+XX"项目，每个都说自己有壁垒，但 90% 的壁垒在 3 个月内被复制。

**标准回答模板**：

```
"我们的壁垒不在单一技术点，而在三个层次的积累：

第一层，数据壁垒（最难复制）：
  XUNO 的推荐越用越准，因为每个用户的穿搭选择都在训练偏好模型。
  竞品从零开始，需要至少 3 个月的用户行为数据才能达到同等精度。
  这不是买 GPU 就能解决的。

第二层，体验壁垒（最难模仿）：
  淘宝/抖音要把 AI 穿搭放在首页，意味着要推翻现有的信息流架构。
  他们的 AI 穿搭是三级页面下的一个功能，我们的 AI 穿搭就是首页。
  大厂不会为了一个功能推翻整个首页。

第三层，场景壁垒（最难覆盖）：
  我们从'面试穿搭'这个最痛的切入点开始，深度覆盖垂直场景。
  大厂做的是通用推荐，不会为'面试穿搭'做专门的规则和对话路径。

补充证据：我们已经在 FashionSigLIP 基础上做了中国数据微调，
  搭配检索准确率比原版提升了 X%（需要实测数据）。
  这个微调的代码和训练数据是我们的核心技术资产。"
```

**🔴 风险点**：如果"微调准确率提升 X%"拿不出实测数据，这段回答直接崩盘。必须在 Demo 前跑完 benchmark。

### 问题 2：你一个人怎么做团队？可持续吗？

**评委为什么问**：互联网+大赛强调团队完整性。一个人项目几乎不可能拿金奖。

**标准回答模板**：

```
"您问得很对，一个人确实不是最优解。但我认为这也是这个项目的特别之处：

首先，我证明了 AI 辅助开发的生产力边界。
  47000 行代码、3 个技术栈（前端/后端/ML）、8 周完成。
  这不是因为我是天才，而是因为 AI 工具（Claude Code、Trae）
  把一个全栈工程师的能力放大了 5-10 倍。

其次，我已经在寻找合伙人。
  校赛后需要补齐的岗位：
  - 运营合伙人（负责用户增长和内容）
  - ML 工程师（负责模型训练和优化）
  我不是一个人在战斗——我的导师 XXX 教授在时尚领域、
  XXX 教授在 AI 领域提供了专业指导。

第三，当前的 Demo 已经证明产品可行性。
  下一步不是'能不能做出来'，而是'能不能运营起来'。
  这确实需要团队，也是我们参加比赛的目的之一——寻找志同道合的伙伴。"
```

**🟠 风险点**：如果评委追问"你找合伙人找了多久了？为什么还没找到？"需要准备一个诚实的回答。

### 问题 3：你的商业模式，数字可信吗？

**评委为什么问**：项目文档中的佣金率、转化率、ARPU 都是理论推算，没有一个经过验证。

**标准回答模板**：

```
"您问到了最关键的问题。我诚实地说：

当前阶段的数字确实是基于行业基准的理论估算，不是实测数据。
  比如电商佣金 4-7%，参考的是淘宝客 2025 年官方公开的服装类目佣金率。
  付费转化率 3-5%，参考的是工具类 App 的行业平均水平。

但这些数字不是凭空想象的。以下是我们的验证计划：

第一步（上线后 1 个月）：
  获取 100 名种子用户，实测核心指标：
  - 推荐点击率（目标 >10%）
  - 试穿使用率（目标 >30%）
  - 付费意愿调研（问卷+访谈）

第二步（上线后 3 个月）：
  如果 CTR >10%，启动小红书内容获客。
  如果 CTR <5%，优先优化推荐质量，不烧钱获客。

我们采取了非常保守的财务假设：
  月成本 400 元（RTX 4060 本地推理 + 免费 LLM + 按需训练）。
  这意味着即使只有 50 个付费用户（9.9 元/人/月），
  也能覆盖基础成本。盈亏平衡点很低。

但我们认为最核心的收入来源不是订阅，而是内容产品——
  个人色彩报告、胶囊衣橱方案——这些是用户为'结果'付费，
  不是为'功能'付费，更符合中国用户的消费习惯。"
```

**🟢 亮点**：诚实承认数据是估算 + 给出验证计划 + 强调低盈亏平衡点。

**🔴 风险点**：如果评委问"你们 100 个种子用户从哪来？获客成本多少？"需要准备更具体的获客计划。

### 问题 4：GLM-4-Flash 免费如果结束了怎么办？你的成本模型就崩了。

**评委为什么问**：文档中多处依赖"GLM-4-Flash 免费"这个前提。

**标准回答模板**：

```
"这是我们风险管理中最重视的问题之一。我们的应对策略是三层的：

第一层：多模型备选链。
  GLM-4-Flash → DeepSeek-Chat（约 0.001 元/次）→ 本地 Qwen2.5-7B。
  RTX 4060 可以运行 7B 量化模型，推理速度约 15 token/s，
  对于穿搭对话（平均 200 token 回复）延迟约 13 秒——可接受。
  成本：电费约 100 元/月，零 API 费用。

第二层：成本控制架构。
  我们的对话不是每个字都走 LLM：
  - 系统消息中的时尚规则（264 条 JSON）由规则引擎直接处理
  - 推荐解释的模板由预生成缓存提供
  - LLM 只负责对话理解和自然语言生成
  实际 LLM 调用量是总请求量的 40-50%。

第三层：收入覆盖。
  即使 GLM 开始收费（按 0.01 元/次计算），
  100 DAU 每人每天 3 次对话 = 900 次/天 = 9 元/天 = 270 元/月。
  加上试穿成本（豆包 0.05 元/次 × 300 次/天 = 450 元/月）。
  总成本约 720 元/月，需要 72 个付费用户即可覆盖。

最坏情况：全部 LLM 调用切到本地 Qwen2.5-7B，
  月成本回到 100-150 元（纯电费），用质量换成本。"
```

**🟢 亮点**：多层备选方案 + 量化成本计算 + 最坏情况有兜底。

### 问题 5：你们的推荐准确率实测是多少？怎么验证的？

**评委为什么问**：推荐系统项目的核心价值就是准确率。没有实测数据等于没有核心价值。

**标准回答模板**：

```
"这是我们最需要补齐的短板，我完全诚实地说：

当前阶段的推荐准确率还没有系统性的用户测试数据。
  但我们做了以下准备工作：

第一，离线评估：
  我们用 100 条 Mock 商品 × 5 种用户 Profile 构建了评估集。
  规则引擎的推荐命中率（用户 Profile 匹配商品属性）约 85%。
  FashionCLIP 向量检索的 Top-5 相关率约 72%。
  这个数据是基于 Mock 数据集的，不代表真实场景表现。

第二，评估框架已就绪：
  我们设计了四维推荐评估体系：
  - 准确率：推荐商品与用户画像的匹配度
  - 多样性：推荐结果的品类/风格覆盖度
  - 新颖性：推荐非热门商品的比例
  - 可解释性：每条推荐有可追溯的推荐理由

第三，上线后的验证计划：
  100 名种子用户 × 2 周使用 → 收集点击/跳过/收藏/购买行为
  → 计算 CTR、转化率、满意度
  → A/B 测试：规则引擎 only vs 规则+CLIP vs 完整管道

我们的目标是上线后 1 个月内给出实测数据。
  在此之前，我们用离线评估作为基准参考。"
```

**🔴 风险点**：这是最致命的问题。如果没有实测数据，评委会认为"推荐系统没有验证过推荐效果"等于"系统没有完成"。

**补救方案**：

- 在 Demo 前至少做 5 个测试用户的定性测试（让他们用，录屏，收集反馈）
- 在 PPT 中放 2-3 张测试用户的反馈截图
- 准备一个"推荐效果对比"的截图（同场景下规则引擎 vs 完整管道的推荐结果）
