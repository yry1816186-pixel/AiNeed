# 寻裳顶层设计总纲

## 1. 先说结论

寻裳现在不是一个单一产品，而是一个“AI 造型师 + 虚拟试衣 + 推荐电商 + 衣橱管理 + 社区内容 + 顾问服务 + 定制服务”的复合平台雏形。能力很多，但北极星不够清晰，导致产品、架构和商业化都在同时发力，容易出现“每个模块都像主角，真正主角反而不够强”的问题。

我建议把寻裳重新定义为：

**面向全年龄段、跨性别、满足平台适龄与合规要求用户的 AI 穿搭决策平台。**

它不是“什么都做一点的时尚 App”，而是帮助用户更快、更准、更放心地回答三个问题：

1. 我今天穿什么。
2. 这件衣服适不适合我。
3. 我值不值得买它。

所有能力都应围绕这三个问题服务。

## 2. 当前项目的真实能力画像

从代码现状看，寻裳已经具备完整的平台级能力：

- 移动端已有 `Home / Stylist / TryOn / Community / Profile` 五大主标签页。
- 移动端已有 14 个 feature 域，覆盖 `auth / home / stylist / tryon / wardrobe / commerce / community / consultant / customization` 等。
- 后端已按 `identity / ai-core / fashion / commerce / social / customization / platform` 分域组织。
- `AppModule` 仍然装配了大批能力：AI 造型、试衣、推荐、社区、博主、顾问、会员、电商、通知、管理后台。
- 推荐引擎目录下已有 27 个服务文件，包含协同过滤、SASRec、知识图谱、向量检索、GNN、LTR 等多种路线。
- AI 侧已有造型师会话、上传照片、生成方案、替换单品、会话日历、配额管理等完整链路。
- 商业化已具备雏形：会员计划、AI 额度、虚拟试衣次数、定制特权、顾问/VIP 门禁。

这说明项目不是“能力不足”，而是“主线过多”。

## 3. 顶层产品定位

### 3.1 核心用户

寻裳不应被定义为“女性产品”，而应被定义为“服务有穿搭与形象决策需求的人”的产品。

建议把服务对象定义为：

- 全年龄段、跨性别、满足平台适龄与合规要求的用户
- 有持续穿搭、形象管理、购物决策或场景着装需求的人
- 在通勤、约会、出游、社交、家庭活动、正式场合、内容表达等场景间切换的人
- 买衣服前犹豫、衣橱利用率低、审美表达不稳定、决策疲劳强的人
- 愿意为“省时间、省试错、更适合自己、更体面地出现”付费的人

但这不代表产品策略必须一开始就平均服务所有人。更合理的做法是：

- 产品定义保持包容，面向全年龄段与跨性别用户
- 运营与增长可以分阶段切入高频需求人群
- 画像与推荐优先按场景、体型、风格、预算、气候、年龄阶段建模
- 性别可以作为辅助信号，但不能成为产品边界或默认前提

### 3.2 北极星价值

寻裳的核心不是“生成图”，也不是“做社区”，而是：

**把穿搭决策从模糊、焦虑、低效，变成清晰、个性化、可执行。**

### 3.3 一句话定位

**寻裳是你的 AI 穿搭决策官，帮你从个人画像、衣橱现状和购买候选中，快速做出更适合自己的穿搭与购买决定。**

## 4. 产品主线重构

### 4.1 核心闭环

寻裳最应该强化的不是“功能广度”，而是下面这条主闭环：

1. 建立个人画像
2. 形成风格与体型理解
3. 连接用户衣橱
4. 给出场景化穿搭决策
5. 对候选单品做适配判断
6. 需要时进入虚拟试衣
7. 满意后收藏、入橱或购买
8. 用反馈继续优化画像与推荐

这个闭环一旦顺，用户会自然形成留存、订阅和购买行为。

### 4.2 产品层级

建议把产品能力分成四层：

#### A. 核心层：必须做强

- AI 造型师
- 个人画像与风格档案
- 衣橱管理
- 场景化推荐
- 商品适配判断
- 虚拟试衣

#### B. 转化层：直接变现

- 会员订阅
- 商品收藏/加购/购买
- 适配解释与购买理由
- 高价值服务入口

#### C. 信任层：增强决策

- 风格报告
- 色彩季型
- 体型建议
- 历史方案沉淀

#### D. 扩展层：暂时降级

- 社区
- 博主体系
- 私人顾问
- 定制设计

这些不是不能做，而是不该在现阶段与主闭环抢前台权重。

## 5. 信息架构建议

### 5.1 当前问题

当前 IA 最大的问题不是功能少，而是入口太平铺：

- `TryOn` 被放成一级标签，但它更像决策动作，不是日常首页。
- `Community` 被放成一级标签，但当前用户的核心任务仍是“穿什么”和“买不买”。
- `Profile` 承载了过多交易、工具、权益和分析入口，既像“我的”，又像“控制台”。
- 首页 Quick Actions 同时推 AI 造型、试衣、购物车、衣橱、风格报告，说明首页仍在“列功能”，不是“引导任务”。

### 5.2 建议的新 IA

建议采用四大一级结构：

1. `Today`
2. `Wardrobe`
3. `Stylist`
4. `Me`

具体含义如下：

#### Today

作为主首页，只做三件事：

- 今日场景推荐
- 候选单品适配判断
- 今日待办动作

例如：

- 今天穿什么
- 本周通勤胶囊衣橱
- 这件裙子适不适合你
- 你的衣橱里已有 2 件可替代

#### Wardrobe

衣橱不是资料页附属物，而应成为核心资产区：

- 衣物录入与标签化
- 穿搭记录
- 低使用率单品提醒
- 缺失单品建议

#### Stylist

AI 造型师作为核心决策引擎独立存在：

- 场景发起
- 多轮对话
- 方案生成
- 方案解释
- 替换单品
- 一键试衣

#### Me

只保留个人中心职责：

- 画像报告
- 会员权益
- 订单/收藏
- 设置

### 5.3 社区与会员的位置

#### 社区

社区不应是现阶段一级核心导航，而应降级为：

- `Today` 中的“灵感流”
- `Product/Outfit` 详情中的真实示例
- `Wardrobe` 中的“借鉴搭法”

也就是说，社区先做“决策证据层”，而不是“独立消费场”。

#### 会员

会员不应只卖“次数”和“权限”，而应卖结果：

- 更稳定的穿搭决策
- 更强的个人画像
- 更多可执行方案
- 更低试错成本

会员入口应该嵌入用户价值被感知的瞬间：

- 方案想继续展开时
- 想保存更多方案时
- 想开启无限试衣时
- 想解锁专属周计划时

而不是孤立的一张价格表页面。

## 6. 商业模式设计

### 6.1 建议的收入结构

现阶段建议按三层收入结构设计：

1. 订阅收入
2. 交易佣金/导购收入
3. 高客单服务收入

### 6.2 订阅分层

建议简化为：

- `Free`：体验画像、有限造型、有限试衣
- `Pro`：无限决策支持、更多衣橱智能、更多试衣额度
- `VIP`：加入人工顾问与高价值服务

其中：

- `Pro` 是主力商业化层
- `VIP` 是高端增值层
- 私人顾问不要成为基础主线，而应作为高 ARPU 附加层

### 6.3 不建议当前重押的方向

- 不建议把社区当成增长主引擎
- 不建议把定制设计当成当前主收入
- 不建议把复杂推荐算法堆叠当成产品价值本身
- 不建议过早把平台铺到“博主生态/品牌生态/顾问生态”三条线同时做深

## 7. AI 顶层设计

### 7.1 AI 应承担什么角色

寻裳的 AI 不应只是接口拼装器，而应是一个“穿搭决策系统”。

建议将 AI 能力分成四层：

#### 第一层：感知层

- 体型分析
- 色彩季型
- 图片解析
- 衣物属性识别
- 用户行为与反馈捕捉

#### 第二层：画像层

- 用户风格画像
- 场景偏好画像
- 衣橱结构画像
- 可购买偏好画像

#### 第三层：决策层

- 今日推荐
- 场景搭配
- 单品适配判断
- 替换单品建议
- 完整方案生成

#### 第四层：执行层

- 虚拟试衣
- 购买转化
- 收藏/入橱
- 反馈回流

### 7.2 竞争壁垒应该放在哪

真正壁垒不在“调用哪个大模型”，而在：

- 用户画像是否持续积累
- 衣橱数据是否真实可用
- 推荐理由是否可解释
- 方案是否能被执行
- 反馈是否进入持续优化

因此，寻裳的 AI 壁垒应该建立在：

**用户风格图谱 + 衣橱图谱 + 场景决策引擎**

而不是建立在“模型数量”和“算法名字”上。

这也意味着，AI 的用户理解应采用“属性建模”而不是“性别预设”：

- 先看场景、气候、年龄阶段、体型、风格偏好、预算、职业/生活方式
- 再把性别、文化偏好、审美标签作为补充上下文
- 避免把“男装/女装”当成默认的一阶决策逻辑
- 优先输出“为什么适合这个人”，而不是“为什么适合某类性别”

### 7.3 AI 中台建议

建议建立统一 AI Platform，包含：

- Task Router：按任务类型路由模型与策略
- Context Builder：统一组装用户画像、衣橱、场景、天气、历史反馈
- Policy Layer：安全、额度、会员权限、隐私规则
- Evaluation Layer：效果、成本、延迟、转化率评估
- Prompt/Workflow Registry：任务模板、版本和灰度

### 7.4 模型与算法策略

推荐引擎当前算法过多，建议重构为三层而不是多条并列主路线：

1. Profile-based rules
2. Retrieval & ranking
3. Generative explanation

具体来说：

- 规则层负责兜底与稳定性
- 检索排序层负责找候选
- 生成层负责解释与交互

GNN、SASRec、知识图谱、向量、LTR 这些应被降级到“可插拔实验策略”，而不是每一个都作为产品叙事中心。

## 8. 技术架构总纲

### 8.1 核心判断

当前最合适的技术路线不是拆微服务，而是继续做：

**强边界的模块化单体 + AI 独立运行时 + 异步任务平台**

理由：

- 业务仍在快速收敛期
- 模块已经很多
- 复杂度主要来自边界不清，不来自部署形态
- 过早拆分只会把组织复杂度提前放大

### 8.2 建议的系统分层

#### Experience Layer

- Mobile App
- Admin Console
- Future Brand/Partner Console

#### Decision Layer

- AI Stylist
- Recommendation Orchestrator
- Wardrobe Reasoner
- Fit & Try-on Decision Engine

#### Domain Layer

- Identity
- Profile Graph
- Fashion Catalog
- Wardrobe
- Commerce
- Social Lite
- Membership

#### Platform Layer

- Notification
- Queue
- Analytics
- Feature Flags
- Observability
- Search

#### AI Runtime Layer

- Model Router
- Prompt/Workflow Registry
- Evaluation
- Safety
- Cost Control

#### Data Layer

- PostgreSQL：主业务数据
- Redis：缓存、配额、会话态
- Object Storage：图片与结果图
- Vector Store：相似检索
- Event / Queue：异步任务

### 8.3 两阶段目标架构

#### 阶段一：聚焦期

目标：把“穿搭决策闭环”打透。

重点动作：

- 收缩前台产品主线
- 把 `AI Stylist + Wardrobe + Recommendation + TryOn` 串成一条
- 推荐引擎做减法
- 社区降级为灵感和证据层
- 顾问与定制降级为高价值附加层

#### 阶段二：放大期

目标：在闭环稳定后，扩张生态与商业深度。

重点动作：

- 放大会员体系
- 逐步增强社区交易联动
- 引入博主/品牌/顾问生态
- 建立品牌侧和运营侧中后台
- 做更完整的实验平台和 AI 评估体系

## 9. 模块取舍建议

### 9.1 应升格为核心的模块

- `ai-stylist`
- `try-on`
- `profile`
- `wardrobe`
- `recommendations`
- `subscription`

### 9.2 应合并或弱化的模块

- `community + blogger` 先统一为灵感内容层
- `consultant` 先作为 VIP 服务插件，不作为核心主路径
- `customization` 先作为高客单附加能力
- `favorites` 应并入衣橱/购买意向体系
- `stock-notification` 应继续作为通知子能力，而非独立产品叙事

### 9.3 当前建议冻结的方向

- Harmony 独立投入
- 复杂推荐算法继续扩张
- 管理后台的广泛铺设
- Code RAG 一类与主业务价值不直接相关的能力

## 10. 用户体验原则

后续所有详细设计都建议遵守这五条原则：

1. 每个页面只回答一个核心问题。
2. 每个关键动作都要能解释“为什么推荐给你”。
3. 虚拟试衣是决策动作，不是独立宇宙。
4. 社区内容要服务决策，不要抢占决策。
5. 会员售卖的是结果和效率，不是权限列表。

## 11. 未来 90 天建议

### 第一优先级

- 明确单一北极星：穿搭决策效率与购买信心
- 重构一级导航与首页结构
- 打通画像 -> 方案 -> 试衣 -> 收藏/购买 -> 反馈闭环

### 第二优先级

- 建立统一用户风格图谱与衣橱图谱
- 收缩推荐策略为少数稳定主链
- 把会员权益重新绑定到结果价值

### 第三优先级

- 社区变成灵感证据层
- 顾问和定制变成高价值服务层
- 建立 AI 评估、成本与灰度能力

## 12. 最重要的一句话

寻裳下一阶段不是继续“加模块”，而是把已经拥有的能力压缩成一个强主线：

**让用户在任何一个穿搭时刻，都能更快做出更适合自己的决定。**
