# 寻裳 XUNO — 绝对最高标准执行协议 v2

> 每次新会话或 GSD 命令启动时注入。这不是建议，是命令。违反任何一条 = 执行失败。

## §0. 两条元规则（覆盖一切场景，包括本文件未写的）

**规则 0-A：主动搜寻，不是被动等待**
不允许"遇到问题再处理"。你必须主动扫描、主动质疑、主动寻找每一个可能的问题、遗漏、次优解。如果一个文件你没读过，你不能假设它没问题。如果一个决策你没验证过，你不能假设它正确。

**规则 0-B：标准取上界，研究取深度**
本文件未覆盖的场景：先研究（≥2 个独立来源），再制定方案，研究深度取行业最高实践水平。如果发现行业标杆比本文件更高，以更高的为准。本文件是下限，不是上限。

## §1. 你在为什么而战

项目：寻裳 XUNO — AI 穿搭决策平台。AI 角色"伊伊"主动推送当日穿搭，零步决策，语音一步触达。

**三条命线同时在线：**

- **比赛**：中国国际大学生创新大赛（原互联网+）。校赛 5-6 月，国赛 9 月。金奖率 5%，AI 赛道竞争最激烈
- **产品**：真实用户第一次打开 App 的 30 秒决定去留
- **创业**：技术壁垒 = 融资故事 = 公司估值

**时间残酷**：距离校赛 < 8 周。每一天的投入必须有可衡量的产出。不允许把时间花在评委看不到、用户感受不到的优化上，除非它是后续功能的硬依赖。

**叙事核心**（每一个决策必须服务于这个故事）：

> "今天穿什么"是每个人每天的第一个决策。但现有方案都是"搜索-筛选-纠结"的工具。XUNO 不是工具，是搭子。伊伊像那个品味好的朋友，在你还没想的时候就把方案递到你面前。这不是 AI 辅助穿搭，这是 AI 替你决策穿搭。体验壁垒替代技术壁垒。

## §2. 执行心智模式（必须内化）

### §2.1 先读再动手

动手前必须读完：

1. `.planning/STATE.md` — 项目当前精确位置
2. 本文件 — 质量标准
3. 当前 phase 的 CONTEXT.md + 所有已完成的 PLAN/SUMMARY — 前人做了什么、遇到了什么、学到了什么
4. `docs/XUNO_FINAL_PLAN.md` — 42 冻结决策（但必须验证前提，见 §2.4）

### §2.2 主动扫描，不留盲区

- 扫描 = 读每一个相关文件，不是抽样检查
- 当你修改文件 A 时，你必须主动检查所有 import A 的文件是否受影响
- 当你新增接口时，你必须主动检查所有消费者是否兼容
- 当你修改数据库 schema 时，你必须主动检查所有查询是否仍然正确
- 不允许"改了这里但没检查那里"

### §2.3 对抗性思维

每个决策在确定前，你必须：

1. **以攻击者视角审视**：这个方案有什么安全漏洞？什么边界情况会崩溃？
2. **以评委视角审视**：评委看到这个会问什么尖锐问题？我能回答吗？
3. **以竞争对手视角审视**：如果我是 Stitch Fix 的工程师，看到这个会怎么想？"就这？"
4. **以最苛刻用户视角审视**：网络差的时候、数据为空的时候、第一次用的时候、用了三个月以后

### §2.4 第一性原理质疑

不允许因为"之前就这么定的"就盲目执行。当你发现以下信号时，必须立即质疑并上报用户：

- 某个决策的前提假设已过时或被证伪
- 某个技术选型在当前上下文中不是最优（比如有更好的替代方案出现）
- 某个需求在当前阶段实际不需要或优先级错误
- 某个架构决策在规模/时间/成本约束下不可行

质疑 ≠ 不执行。质疑 = 先研究验证，确认后执行或修正后执行。

### §2.5 时间感知

距离校赛不到 8 周。每一个技术决策必须回答：

- 这个投入对评委可见吗？（直接或通过 demo/PPT）
- 这个投入对用户可感知吗？
- 如果不可见/不可感知，它是后续哪项可见功能的硬依赖？
- 有没有更快的方式达到 90% 的效果？

**80/20 铁律**：花 20% 时间达到 80% 效果的方案，优于花 100% 时间达到 100% 效果但延误 deadline 的方案。但 80% 的标准必须高于竞品。

## §3. 六维绝对标准

### §3.1 工程极致

| 维度     | 绝对标准                                                                 | 触及红线 = 立即停止并修复          |
| -------- | ------------------------------------------------------------------------ | ---------------------------------- |
| 类型安全 | 零 `any`，零 `@ts-ignore`，所有泛型参数明确，strict 模式全开             | 任何 `any` 入库                    |
| 测试     | 核心路径 80%+ 覆盖，新增代码 100% 覆盖，每个 bug 必须先写回归测试再修    | 新功能零测试 / 修 bug 不写回归     |
| 安全     | OWASP Top 10 全覆盖，PIPL 每项敏感数据单独同意，密钥零硬编码，输入全验证 | 明文密码/未验证输入/敏感数据无授权 |
| 性能     | API P99 < 500ms，首屏 < 2s，列表 60fps，无内存泄漏                       | 可感知卡顿/白屏/OOM                |
| 架构     | routes→services→data 严格分层，feature-based，单向依赖，接口契约版本化   | 循环依赖/跨层直接调用              |
| 代码     | 函数 < 50 行，文件 < 400 行，圈复杂度 < 10，无重复逻辑                   | 1000+ 行/5+ 层嵌套/复制粘贴        |
| 变更安全 | 每个变更可独立回滚（git commit 粒度 = 一个逻辑变更）                     | 无法回滚的大批量变更               |

### §3.2 产品极致

| 维度     | 绝对标准                                                                  |
| -------- | ------------------------------------------------------------------------- |
| 第一印象 | 30 秒内看到伊伊的第一个推荐。不是空白，不是 loading，是具体的穿搭方案     |
| 交互     | 每个操作有即时反馈：skeleton/pulse/haptic，零"点了没反应"                 |
| 视觉     | 全局 DesignTokens，零硬编码颜色/间距/圆角，对比度 ≥ 4.5:1                 |
| 空状态   | 每个列表/页面 = 插画 + 文案 + 行动按钮。不允许空白                        |
| 错误     | 友好中文 + 重试路径 + 自动上报。不允许技术异常暴露给用户                  |
| 离线     | 核心数据本地缓存，断网可浏览衣橱/日历/已保存推荐                          |
| 包容     | 零性别偏见，body-positive（描述衣服不描述身体），试穿失败归因于服装非用户 |
| 情感     | 伊伊不是工具，是朋友。每次交互必须有人格温度：有主见、会关心、偶尔开玩笑  |

### §3.3 比赛极致

**金奖铁律（基于 2024 国赛 230 个金奖项目分析）：**

1. **30 秒定律**：开场 30 秒必须让评委产生"有意思"的直觉。用真实用户故事或数据钩子，不是功能列表
2. **数据不说谎**：不说"精准推荐"，说"Recall@10 提升 X%，用户满意度 Y%"。每个技术声明有 benchmark
3. **真实用户 > 一切**：1 个真实种子用户的反馈 > 100 页商业计划书的理论分析
4. **社会价值是记忆点**：包容性穿搭服务被忽视群体（中老年/非标准体型），这是评委记住我们的理由
5. **垂直 > 广泛**：我们不是"AI+时尚"，是"AI 替你决策今天穿什么"。越窄越锐

**AI 项目一票否决（必须逐条确认我们没踩）：**

- [ ] 套壳 GPT（API 调用无自研）
- [ ] 夸大 AI 能力（无 benchmark）
- [ ] 训练数据来源不明
- [ ] 忽视隐私/伦理
- [ ] 伪需求（用户并不需要）
- [ ] 万亿市场但说不清和自己的关系

**物质清单（校赛前必须完成）：**

- [ ] 1-3 分钟 Demo 视频（真实产品画面，前 15 秒用场景钩子）
- [ ] 15-20 页路演 PPT（图表 ≥ 60%，结构：痛点 → 方案 → 技术 → 市场 → 竞品 → 数据 → 团队）
- [ ] 技术架构图 + 6 层推荐漏斗可视化
- [ ] 竞品对比矩阵（≥5 竞品 × ≥8 维度）
- [ ] 财务模型（月成本精确到 10 元，12 个月增长预测）

### §3.4 创新极致

每个 phase 结束时强制回答（不允许跳过任何一条）：

1. **差异化**：这组功能全球有谁在做？他们的本质局限是什么？我们做了什么他们做不到的？
2. **AI 独创**：是否利用 AI 创造了传统方案不可能的体验？（不是"AI 替人工"，是"AI 催生新范式"）
3. **Wow 因子**：用户第一次看到会"哇"吗？如果不会，差什么？怎么补？
4. **数据飞轮**：用户使用 → 什么变好 → 用户更离不开 → 正循环如何闭合？

### §3.5 研究极致

**每个重大决策前必须研究。不允许凭经验/直觉拍板。**

| 决策类型 | 最低研究深度                                                  | 最低来源数 |
| -------- | ------------------------------------------------------------- | ---------- |
| 技术选型 | 对比 ≥3 个候选 × ≥6 个维度（性能/生态/维护/成本/风险/适配性） | 3          |
| 架构设计 | 分析 ≥2 种方案，各有完整 pros/cons + 规模验证案例             | 2          |
| 产品功能 | 竞品实现 + 用户痛点 + 学术前沿，缺一不可                      | 2          |
| 比赛策略 | 近 3 年同赛道获奖项目 ≥3 个的结构化分析                       | 2          |
| 性能优化 | Benchmark 数据 + 真实测试 + 业界标杆，三者取最高              | 2          |

### §3.6 管理极致

| 维度       | 绝对标准                                                             |
| ---------- | -------------------------------------------------------------------- |
| 状态可追踪 | 新会话读 STATE.md 即可 100% 接手，零信息丢失                         |

## §4. 能力不足 → 不降标准 → 强制研究

**任何维度不确定时，执行以下协议，不允许降低标准：**

```
IF 不确定技术选型
  → 并行启动 3 agent：官方文档深研 + 社区实践验证 + 竞品实现分析
  → 输出：≥3 候选 × ≥6 维度对比矩阵 + 推荐理由 + 风险标注

IF 不确定代码质量
  → 并行启动：code-reviewer + security-reviewer + performance-optimizer
  → 输出：按严重性排序的修复清单 + 修复后验证结果

IF 不确定产品体验
  → 并行启动：UX Researcher + Accessibility Auditor
  → 输出：交互流程图 + 竞品截图对比 + 无障碍合规报告 + 具体改进代码

IF 不确定比赛策略
  → deep-research：近 3 年互联网+国赛 AI 赛道获奖项目
  → 输出：对标分析 + 差异化建议 + 评委可能提问 10 条 + 回答预案

IF 不确定创新方向
  → 并行 3 agent：arxiv/scholar 论文 + Product Hunt 海外产品 + 国内趋势
  → 输出：创新机会清单 + 可行性评估 + 落地方案 + 对现有设计的影响

IF 遇到本文件未覆盖场景
  → §0-B：先研究（≥2 来源），再制定方案，标准取行业最高
  → 将新场景和标准补充到本文件
```

**绝对禁止：** 降低标准 / 跳过研究 / 凭直觉选方案 / 假装完成 / 用空话搪塞 / 说"差不多了"。

## §5. GSD 工作流强制检查点（弥补系统已知盲区）

### §5.1 研究阶段完成后

- [ ] 交叉验证：检查 4 个并行研究 agent 的发现是否矛盾（如 Stack 推荐 A 但 Pitfalls 标记 A 有致命问题）
- [ ] 补充维度：成本分析、性能基线、合规要求、无障碍标准（GSD 默认不研究这 4 项）
- [ ] 决策压力测试：逐条验证 42 项冻结决策的前提假设是否仍成立，标记过时决策

### §5.2 每个 Plan 开始前

- [ ] 成功标准包含量化阈值（不允许只有"可观测行为"无数值）
- [ ] 高风险项优先（fail fast），不允许把高风险推迟到最后
- [ ] 本 plan 的交付物独立可演示（不是纯内部重构，除非是后续硬依赖）
- [ ] 明确验证方式：自动化测试 or 手动验证步骤（不允许"看一眼就过了"）

### §5.3 代码执行时

- [ ] TDD：先写测试 → 红 → 实现 → 绿 → 重构（纯 UI 调整除外）
- [ ] 跨服务变更必须同步更新接口契约（Python ↔ NestJS ↔ RN 的类型定义）
- [ ] 每个 git commit = 一个逻辑变更（可独立回滚）
- [ ] plan 执行完立即更新 STATE.md（不允许批量更新）

### §5.4 验证时

- [ ] 验证行为 ≠ 验证代码存在。代码存在不算完成，行为正确才算
- [ ] 必须包含 ≥1 个负面测试（错误路径/异常输入/网络断开）
- [ ] 所有"需人工验证"项必须记录在 STATE.md，下一个会话首件事就是验证

### §5.5 Phase 之间

- [ ] 回归验证：上个 phase 的关键行为仍然正确
- [ ] 学习提取：`/gsd-extract-learnings` → 写入后续 phase CONTEXT.md
- [ ] 决策追踪：PROJECT.md Key Decisions Outcome 列更新
- [ ] 风险审查：更新风险注册表，关闭已缓解的风险，添加新发现的风险
- [ ] 健康检查：`/gsd-health`，确认项目状态清洁
