## 1. 北极星定义

### 1.1 产品定位

**寻裳是面向全年龄段、跨性别、满足适龄与合规要求的 AI 穿搭决策平台。**

平台只围绕三个核心问题组织一切能力：

1. **我今天穿什么** — 场景化穿搭方案
2. **这件衣服适不适合我** — 候选单品适配判断
3. **我值不值得买它** — 购买决策辅助

### 1.2 核心原则

- **属性优先，身份辅助**：用户建模围绕场景、体型、尺码、风格、预算、气候展开，性别仅为可选辅助信号
- **决策优先，功能从属**：首页是决策入口，不是功能目录
- **闭环优先，能力从属**：推荐 → 试穿 → 购买 → 反馈必须形成闭环，各 AI 能力不再各说各话
- **工程为产品服务**：每个工程修复必须推进产品目标，不是为整洁而整洁

### 1.3 非目标

- 不以"女性时尚 App"作为定位
- 不把社区做成第一主入口（v1 不设社区 Tab）
- 不把虚拟试衣做成独立产品中心
- 不以扩充算法名词和模型种类作为核心竞争力叙事
- 不优先拆微服务
- 不把会员权益设计成纯权限堆砌

## 2. 导航与信息架构

### 2.1 一级导航

收敛为 4 Tab：

| Tab      | 名称   | 职责                      | 核心任务                         |
| -------- | ------ | ------------------------- | -------------------------------- |
| Today    | 今日   | 当天决策入口              | "今天穿什么" + "现在怎么搭"      |
| Discover | 探索   | 商品发现 + 衣橱管理混合体 | 搜索/浏览/衣橱/缺口补全          |
| Stylist  | 造型师 | AI 深度决策中心           | 对话式造型 + 方案生成 + 试衣动作 |
| Me       | 我的   | 个人中心                  | 画像/偏好/会员/订单/设置         |

### 2.2 Tab 详细说明

#### Today（今日）

首页回答三个问题：今天穿什么、现在最该做什么、这件适合我吗。

内容结构（从上到下）：

```
1. 场景卡：天气 + 星期 + 用户选择的今日场景 + AI 一句话摘要
2. 今日方案：2-3 套完整搭配（标注哪些来自衣橱）
3. 候选适配：待决策商品的适配判断
4. 衣橱洞察：缺口提醒 + 季节建议
5. 灵感区：社区内容按当前场景筛选（30% 空间）
```

降级策略：AI 推荐管道不可用时，用天气 + 季节 + 星期几 + 场景模板生成规则化方案。

#### Discover（探索）

解决"衣橱对新用户是空白页"的问题。冷启动时展示推荐单品，积累后渐变为衣橱管理。

内容结构：

```
冷启动用户：
  1. 为你推荐：基于 Onboarding 画像的精选单品
  2. 百搭基础款：按场景推荐高频单品
  3. 搜索栏：自然语言搜索 + 分类浏览
  4. 入口："拍照添加到衣橱"引导

有衣橱用户（>5件）：
  1. 我的衣橱：分类浏览 + 穿搭统计
  2. 缺口推荐：基于现有衣橱的补全建议
  3. 百搭基础款：持续推荐
  4. 搜索 + 分类浏览
```

#### Stylist（造型师）

AI 深度决策中心。对话式交互，单屏体验（不分裂为双屏）。

核心能力：

```
- 对话式穿搭咨询
- 方案生成（搭配 + 理由 + 替代 + 下一步动作）
- 虚拟试衣（嵌入对话流的动作，非独立页面）
- 连续穿搭计划（出差/旅行/一周计划）
```

#### Me（我的）

个人中心，包含：个人资料、偏好管理、会员、订单、衣橱统计、设置、社区入口（深层页面）。

### 2.3 功能降级映射

| 当前功能     | 新位置                                    | 说明                   |
| ------------ | ----------------------------------------- | ---------------------- |
| 虚拟试衣 Tab | Stylist 内动作 + Today 方案内按钮         | 从一级入口降为决策动作 |
| 社区 Tab     | Today 灵感区 + 商品详情内嵌 + Me 深层入口 | 从主线降为证据层       |
| 博主生态     | Me 深层页面                               | 不占主线               |
| 顾问/定制    | Me 内 VIP 服务入口                        | 高价值扩展服务         |
| 风格报告     | Me > 画像报告                             | 可分享的内容产物       |

## 3. 用户模型

### 3.1 六层用户画像模型

```
L1: Compliance Profile（合规层）
    ageBand: "teen" | "young_adult" | "adult" | "midlife" | "senior"
    safetyLevel: "standard" | "restricted"
    guardianMode: boolean

L2: Fit Profile（体型层）
    height: number
    weight: number
    bodyMeasurements: { bust, waist, hip, shoulder, inseam }
    bodyType: "apple" | "pear" | "hourglass" | "rectangle" | "inverted_triangle"
    usualSize: "XS" | "S" | "M" | "L" | "XL" | "XXL"
    fitPainPoints: string[]

L3: Style Profile（风格层）
    styleExpression: "简洁利落" | "柔和优雅" | "中性平衡" | "个性实验" | "随性自在"
    preferredAesthetics: string[]
    avoidances: string[]
    formalityPreference: "casual" | "smart_casual" | "formal"
    colorPreferences: string[]
    colorSeason: string

L4: Context Profile（场景层）
    primaryScenarios: string[]  // 通勤/约会/休闲/运动/正式/聚会/校园/旅行
    weather: string
    city: string
    budgetBand: "budget" | "mid_range" | "premium" | "luxury"
    dressCode: string
    calendarContext: string

L5: Wardrobe Graph（衣橱层）
    ownedItems: ClothingItem[]
    usageFrequency: Map<itemId, number>
    gaps: string[]
    recentLooks: Outfit[]

L6: Optional Identity Signals（可选身份层）
    gender: "male" | "female" | "other" | null
    genderExpression: string | null
    culturePreference: string | null
    garmentPreference: {
      lowerBody: "pants" | "skirts" | "both"
      onePiece: "dresses" | "jumpsuits" | "none"
      hosiery: "tights" | "socks_only"
    } | null
```

### 3.2 关键设计决策

1. **gender 是 L6 可选字段**，不进入 L1-L5，不参与 Profile 完整度主权重
2. **garmentPreference 替代性别做单品推荐**：知道用户是否穿裙子比知道性别更有用
3. **ageBand 是 L1 必填字段**，用于合规控制和内容边界
4. **styleExpression 是 L3 必填字段**，比性别更接近真实穿搭决策
5. **primaryScenarios 是 L4 必填字段**，场景是推荐最强信号

### 3.3 Profile 完整度权重

```
场景信息 (primaryScenarios)        20%
尺码/体型 (height+weight+bodyType)  25%
风格偏好 (styleExpression+color)    20%
衣橱数据 (wardrobeItems count)      20%
照片/视觉 (photoUri+colorSeason)    15%
gender                              0%（不计入主权重）
```

## 4. Onboarding 流程

### 4.1 设计原则

- 属性优先：场景 > 体型 > 风格 > (性别)
- 50 秒必填步骤 + 可选延展
- 价值前置：第一步就让用户看到"这和我有关"

### 4.2 四步流程

**Step 1: "你的日常场景"（15 秒）— 新增**

展示 8 个场景卡片（可多选 1-3 个）：

```
通勤 / 约会 / 休闲 / 运动 / 正式场合 / 聚会 / 校园 / 旅行
```

数据字段：`primaryScenarios: string[]`（必填）

**Step 2: "认识你"（15 秒）— 重构**

```
年龄段（横排 pills，单选）：16-22 / 23-28 / 29-35 / 36-45 / 46-55 / 55+
身高/体重（并排输入框）
常穿尺码（下拉选择）
```

数据字段：`ageBand, height, weight, usualSize`

gender **已移除**（可在 Profile 设置页选填）

**Step 3: "你的风格"（12 秒）— 重构**

两段式：

```
a. 风格表达（5 选 1）：简洁利落 / 柔和优雅 / 中性平衡 / 个性实验 / 随性自在
b. 穿搭图选择（选 3 张喜欢的）：展示 9 张覆盖不同风格的穿搭图
```

数据字段：`styleExpression, styleImageSeeds`

穿搭图选择的目的：系统提取 FashionCLIP 嵌入作为推荐种子，比文字问卷更准确。

**Step 4: "就快好了"（8 秒）— 可跳过**

```
- 照片上传（可选）："上传照片让 AI 更懂你的体型和色彩"
- 衣橱连接（可选）："拍照录入已有衣物，获得更精准推荐"
- 完成/跳过
```

### 4.3 冷启动推荐策略

| 阶段       | 策略                               | 数据来源                                                 |
| ---------- | ---------------------------------- | -------------------------------------------------------- |
| 0-3 次推荐 | 场景 + FashionCLIP 种子 + 规则引擎 | Onboarding primaryScenarios + styleImageSeeds + bodyType |
| 3-10 次    | 画像 + 行为混合                    | 规则引擎(60%) + 热门排序(25%) + LLM 推理(15%)            |
| 10+ 次     | 行为驱动                           | SASRec(40%) + FashionCLIP 向量(30%) + 规则引擎(30%)      |

## 5. 推荐系统架构

### 5.1 核心策略：简化为 3 层

```
规则兜底 → 检索排序 → 生成解释
```

**保留的 3 个策略**：

| 策略                 | 组件                                  | 权重       | 说明                                   |
| -------------------- | ------------------------------------- | ---------- | -------------------------------------- |
| 规则引擎             | MatchingTheoryService + JSON 规则文件 | 冷启动主力 | 264+ 条结构化规则，体型/色彩/面料/场景 |
| FashionCLIP 向量检索 | VectorSimilarityService + Qdrant      | 视觉核心   | 服装图像嵌入，"视觉相似"和"搭配兼容"   |
| SASRec 序列推荐      | sasrec_service.py                     | 行为辅助   | 捕捉用户浏览序列模式                   |

**砍掉的 2 个策略**：

| 策略                                     | 原因                                                           |
| ---------------------------------------- | -------------------------------------------------------------- |
| 协同过滤 (CollaborativeFilteringService) | 伪实现（只是同品类加分），用户量 < 1 万时数据密度不足          |
| 知识图谱 (KnowledgeGraphService)         | 内存硬编码图，覆盖率不足，场合匹配和风格兼容逻辑合并到规则引擎 |

### 5.1.1 关键路径降级策略

| 故障场景                 | 降级行为                                            | 用户感知                          |
| ------------------------ | --------------------------------------------------- | --------------------------------- |
| AI 推荐管道不可用        | Today Tab 用天气+季节+星期几+场景模板生成规则化方案 | "今天降温了，推荐穿..."仍然有内容 |
| 虚拟试穿 API 超时/不可用 | 跳过试穿，直接展示文字版搭配建议+尺码推荐           | "根据你的体型，M 码应该合适"      |
| 商品搜索 API 超时        | 展示本地缓存的热门商品 + "稍后再试"提示             | 推荐流不空白                      |
| LLM 服务不可用           | Stylist 对话降级为预设 FAQ 回复                     | 基础问题仍可回答                  |
| FashionCLIP 服务不可用   | 降级到规则引擎单独驱动推荐                          | 推荐质量下降但不空白              |
| 用户无衣橱数据           | 跳过 L6 衣橱互补层，只依赖 L1-L5                    | 不影响新用户                      |

### 5.2 六层漏斗管道

推荐排序执行顺序（对应六层用户模型）：

```
Step 1: L1 合规过滤（硬排除）
  → ageBand 不符的商品直接排除
  → safetyLevel=restricted 时排除成人化/性感化内容

Step 2: L2 场景过滤（硬排除）
  → occasion 不匹配直接排除
  → season 不匹配直接排除
  → weather 不匹配直接排除

Step 3: L3 尺码过滤（硬排除）
  → sizeCurve 与用户 usualSize 不兼容的排除
  → fit 与用户 bodyType 明确冲突的排除

Step 4: L4 预算过滤（硬排除）
  → price > budgetBand 上限的直接排除

Step 5: L5 风格评分（加权评分 — 核心推荐层）
  → SASRec 序列信号:    0.25
  → FashionCLIP 向量:   0.30
  → 规则引擎(体型+色彩+面料+场景): 0.30
  → 热门度:             0.15

Step 6: L6 衣橱互补加分（软加权）
  → 与用户已有衣橱单品可搭配的加分
  → 填补衣橱缺口的加分
```

### 5.3 推荐输出结构

每条推荐必须包含：

```typescript
interface RecommendationOutput {
  items: ClothingItem[]; // 推荐的单品列表
  outfit: OutfitSuggestion; // 完整搭配方案
  explanation: {
    why: string; // "选这件因为它和你的黑色西装外套很搭"
    alternative: ClothingItem[]; // 1-2 个替代选项
    nextAction: "tryOn" | "saveToWardrobe" | "addToCart" | "askStylist";
    confidence: number; // 0-1 推荐置信度
  };
}
```

### 5.4 时尚规则整合

**关键问题**：当前 `full_outfit_engine.py` 内硬编码了简化版规则，与 JSON 规则文件（264+ 条详细规则）不一致。

修复方案：

1. FullOutfitEngine 从 JSON 规则文件动态加载规则，替代硬编码
2. `chinese_occasion_rules.json` 的丰富内容通过 RAG 注入 AI Stylist 上下文
3. `item_compatibility.json` 的 compatibility_score 直接用于单品兼容度计算
4. `fabric_rules.json` 的面料兼容矩阵接入评分权重

### 5.5 时尚规则遗漏修复

| 问题                                                      | 文件                      | 修复                                                                         |
| --------------------------------------------------------- | ------------------------- | ---------------------------------------------------------------------------- |
| above_30 温区 8 个场合 tips 完全相同                      | weather_outfit_rules.json | 按场合差异化重写（户外运动/通勤/约会的高温策略完全不同）                     |
| 0_10 温区面试场景 layer_details 写 ["单层","单层","单层"] | weather_outfit_rules.json | 改为 ["内搭","毛衣/针织","大衣/厚外套"]，recommended_materials 补充羊毛/羊绒 |
| 推荐内容隐性女性偏移（"加绒连裤袜"、"铅笔裙"等）          | 多个规则文件              | 改为属性描述而非品类名称，或按 garmentPreference 条件推荐                    |

## 6. 虚拟试衣

### 6.1 当前状态

**试衣系统已经是无性别的** — 输入是 photo + item，处理是 MediaPipe 关键点 + CIELAB + 云端 API，完全不读用户性别。不需要大的修改。

### 6.2 定位调整

- 虚拟试衣从独立 Tab 降为决策动作
- 嵌入到 Stylist 对话流和 Today 方案卡中
- 试衣结果必须带出：可信度、误差来源、适用边界
- 试衣不单独追求"好看"，而是服务"是否适合、是否值得试、是否值得买"

### 6.3 试衣结果输出

```typescript
interface TryOnResult {
  image: string; // 试穿效果图
  confidence: number; // 整体可信度
  fitAssessment: {
    overall: "good" | "acceptable" | "poor";
    details: { area: string; assessment: string }[];
  };
  suggestion: string; // "这个版型很衬你的肩线"
  alternatives: ClothingItem[]; // 如果不适合，推荐什么版型
  scenes: string[]; // "适合在通勤/日常场景穿"
}
```

## 8. 会员与商业化

### 8.1 三层混合模型

```
Layer 1: 免费层（获客）
  每日 5 次 AI 对话
  每日 3 次虚拟试穿
  基础推荐（无个性化解释）
  基础衣橱管理（20 件）

Layer 2: 内容产物付费 — 19 元/月 | 49 元/季 | 168 元/年
  个人色彩季型报告（可视化 PDF，可保存可分享）
  体型分析报告（轮廓图 + 建议）
  胶囊衣橱方案（3 套/月）
  无限试穿 + 高清效果图
  个性化推荐解释
  [可感知的内容产物，不是"更快更好更多"]

Layer 3: 体验升级 + 电商佣金
  高级会员（49 元/月）：
    连续穿搭计划（出差/旅行/一周）
    深度衣橱诊断
    AI 主动推送（"明天降温了，要不要看看保暖搭配？"）
  交易抽佣：
    穿搭方案一键购买（佣金 8-12%）
    顾问预约（抽佣 15-20%）
```

### 8.2 会员触发场景

会员售卖绑定结果，不绑定身份：

- 想继续展开更多方案时
- 想保存色彩/体型报告时
- 想解锁更完整的试衣建议时
- 想获得连续穿搭计划时
- 衣橱管理超过 20 件时

### 8.3 ARPU 修正预期

```
阶段 1（0-1 万用户）：
  付费转化率：3-5%
  加权 ARPU：2-4 元/月
  月收入覆盖不了成本，需资金支持

阶段 2（1-10 万用户）：
  付费转化率：5-8%
  电商佣金 ARPU：5-15 元/月
  可能盈亏平衡

阶段 3（10 万+用户）：
  收入结构从"会员为主"转向"电商佣金为主"
  需要 GMV 做支撑
```

## 11. 体型计算去性别化

### 11.1 BodyMetricsService 修改

当前 `gender = user?.gender || Gender.female` 是最危险的设计。

修改方案：

```typescript
// 体脂率：用 waist/hip ratio 作为连续变量选择公式系数
// 而不是二值性别切换

// BMR：改用 Katch-McArdle 公式（基于瘦体质量，完全不依赖性别）
// BMR = 370 + 21.6 * leanMass
// leanMass = weight * (1 - bodyFatPct / 100)

// 体脂分类：不再分男女不同阈值，改用百分位排名
```

### 11.2 ColdStartService 修改

当前 `demographicRules` 按 male/female 分桶。

改为：用 bodyType + styleExpression + primaryScenarios 驱动冷启动推荐。

### 11.3 ProfileCompletenessService 修改

gender 从 10% 权重降为 0%。按 §3.3 新权重重算。
